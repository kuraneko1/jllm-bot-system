# x230 本番切り替え手順書（承認前・未実施）

この文書は作業手順の案であり、切り替えの承認、旧新の完全互換、バックアップの完成や復旧可能性を示すものではありません。実環境の停止・コピー・設定変更・接続・起動は、以下のゲートを満たし、対象と操作を現地で検証したうえで別途承認を得てから担当者が実施します。自動切り替えスクリプトはありません。

参照: [調査記録](<x230-cutover-investigation.md>)、[旧設定の対応表](<legacy-configuration-map.md>)、[限定スナップショットの仕様と制限](<../tools/offline_snapshot.md>)、[明示台帳のスナップショット](<../tools/tree_snapshot.md>)、[本番構成の雛形](<../profiles/production.example.yaml>)、[CLI](<../src/jllm/cli.py>)。調査記録は調査時点のコード・状態です。その後の変更を含め、**実際に配布する revision とテスト結果を再確認**してください。本文・チケット・ログに秘密、実 ID、実 URL、保護対象のデータや本番用コピーの内容を記録しないでください。

## 0. 実施前のゲート（すべて必須）

- [ ] 責任者、実行者、検証者、連絡先と判断権限を決め、利用者への通知、停止開始・終了予定（タイムゾーンを明記）、監視期間、切り戻し判断期限、最大停止時間、許容データ損失と失敗時の延長判断を合意する。未承認なら着手しない。
- [ ] 現在の旧・新 revision、依存、サービス定義、作業ディレクトリ、トークン供給方法、タイマー、手動起動や自動再起動を棚卸しし、停止・起動・復旧手順を隔離環境で試す。旧サービスは調査時に自動再起動設定だったため、停止指示だけでなく再起動抑止とプロセスの終了まで確認する。新側のサービス名・起動方法・再起動抑止方法は現地で特定する。
- [ ] 書き込み元を Bot 以外も含め列挙する。旧 `jllm-voice-export.timer` は調査時、起動後3分から **15分間隔**で export service を起動していた。タイマー停止だけではすでに動いている export service は止まらない。実行中ジョブの完了・停止と他の手動／定期 writer も確認する。確認できなければ中止する。
- [ ] 実データ、設定、秘密・外部鍵、コード・依存、ディレクトリ、所有権・権限を含む**完全な退避対象一覧と復元手順**を確定する。復元先のアクセス制御、暗号化、空き容量、保管期限、同一障害領域から独立した保管先を承認する。
- [ ] 完全バックアップを取得し、隔離先への復元と DB 整合性・参照・アプリ機能・権限を検証する。新側の書き込み後を含む逆変換／旧側復旧を試し、戻せないデータと許容損失を合意する。失敗、未実施、対象漏れがあれば切り替えない。
- [ ] 実機に触れない自動テストと、隔離データ・テスト用 Bot の試験を完了する。下記の実 Discord・音声等の項目も適切な権限と承認を得て検証する。未検証箇所は明示し、判定者が切替可否を判断する。
- [ ] 設定、全9 TTS、状態、ファイルパス、認証、権限、スコープ、画像生成停止状態、外部公開範囲の対応表を保護された場所でレビューし、対象ファイルの作業用コピーを作成・保護する。雛形や調査の仮値は本番値ではない。

### 限定スナップショットと完全バックアップは別物

[限定スナップショット](<../tools/offline_snapshot.md>) は指定ディレクトリ直下の明示したファイルのみが対象です。[階層スナップショット](<../tools/tree_snapshot.md>) は、事前に人が作成した全要素・種別の台帳と完全一致する階層を扱いますが、台帳の正しさ、停止状態、入力ツリー外のデータ、元の所有者・権限・時刻や業務上の整合性を保証しません。どちらも秘密を含む出力を作り、旧形式への逆変換をしません。**現行本番全体のバックアップ・復元としては未検証**です。verify 成功や旧リリースのコード退避を、完全バックアップ・業務上の復旧成功の代わりにしないでください。SQLite の WAL／journal などの停止条件にも従い、残存時に消去して進めないこと。

## 1. 設定とパスの対応付け

新側には雛形をそのまま使わず、アクセス制限されたローカルコピーを別途作ります。実値は Git、文書、ログ、コマンド履歴や画面共有に出さないこと。次は対応先の確認項目であり自動変換の保証ではありません。

| 旧側の項目 | 新側で確認する場所・注意点 |
| --- | --- |
| `DISCORD_TOKEN` | `adapter.discord.config.token_env` が指す環境変数として安全に渡す。値を YAML や引数に書かない。 |
| `MESSAGE_CHANNEL_WHITELIST` | `feature.reader.config.allowed_channel_ids` と、必要なら `feature.translation.config.allowed_channel_ids` の整数配列。空リストの意味は機能や revision に依存するため、拒否・許可・例外を実テストし、空を安全と仮定しない。 |
| `GLOBAL_REACTION_WORDS` | `feature.reader.config.global_reaction_words` の文字列配列。読み上げ以外の反応範囲も確認。 |
| `DEFAULT_SPEED`、`VC_ANNOUNCEMENT_ENABLED`、`DEFAULT_SPEAKER`、その他再生設定 | reader と speech.playback の両方に適用される項目を個別に設定し、voice.settings の入室音声、履歴、cache 上限も合わせる。`DUCK_ENABLED` は reader と playback に設定し、曲線ファイルは dashboard 側も対応させる。 |
| `OWNER_ID`、`TTS_SWITCH_USER_IDS` | `owner_id` は reader・translation・media に、`tts_switch_user_ids` は reader・translation に対応付ける。コマンドごとの管理権限は値が一致しても同じとは限らない。 |
| `DATA_DIR` と個別パス | `storage.local.config.data_dir` と Reader・各 provider・dashboard・WavRank 等の個別パスをそれぞれ確認。`DATA_DIR` を渡すだけでは profile の `data_dir` は変わらない。旧の個別指定・旧配置優先規則も調べる。 |
| 旧 TTS の設定・選択状態 | 9系統の provider instances、bindings、`tts.router.config.backend_ids` の完全 ID→旧 ID の一意な全対応、`backend_displays` による旧表示名、state の preferred／active／streaming・failover・声・URL を確認。`require_existing_state: true` は不在・不正な状態を拒否するが、別環境の有効な状態を正しいものと識別できない。指定しない場合も、壊れた JSON・未知 ID は起動を止める（黙って先頭へ戻さない）。雛形は1系統のみ。旧に戻す場合も双方向の対応を検証。 |
| 旧トグル・辞書・制限・利用者設定 | 新側の実際の保存先と既存ファイルを照合。`feature.reader.config.require_existing_toggles: true` は既存トグルの不在・不正を拒否する。特に画像生成の停止状態と wav 状態を起動・再起動・切り戻しで確認し、不明なら公開しない。 |
| `MEDIA_APPROVER_ID`、`HTML_REQUIRE_APPROVAL` | media と html-library の承認者を揃え、html-library の require_approval を設定する。両 store を有効にすると media 側の承認者が優先される経路がある。 |
| 認証ファイル、Web 公開設定 | `web.dashboard.config.auth_file`、そのパスから導かれるパスキーファイルと `require_existing_passkey`、既存パスキー、RP ID、origin、TLS と代理サーバを検証。`webchat_dir`・`duck_curve_path` も必要に応じ指定する。未確認のまま外部公開しない。 |
| `MIQ_WORDS`、`KITASAN_ENABLED`、`KITASAN_WORDS` など | Miq と今北産業の起動条件・発火語・制限を各 feature に移し、読み上げ・翻訳からの除外判定も合わせて試す。Miq のフォント・ログ・emoji キャッシュの保存先も確認する。 |
| `MYTALK_HIDDEN_VOICES`、`AUDIO_*` | `feature.reader.mytalk_hidden_voices` と `dictionary.sound.audio_processing`（しきい値・前後の余白・ラウドネス）。旧の非表示話者と音声整形の再現を実音声で確認する。 |
| LLM、翻訳、外部 API、鍵、モデル・RPM | provider / router / feature ごとの設定と鍵ファイルの参照先を照合。router は自身の local / sarashina / atmos の設定から client を作るため、provider 設定だけを移しても不十分。Sarashina のモデル別 RPM を含め、雛形の値や既定が旧設定と等しいとは限らない。 |

### 明示ファイルの読み込み

旧実装は dotenv の後に policy を上書きで読みます。新 CLI では自動探索せず、必要なときだけ `--env-file` と `--policy-file` を明示します。優先順位は **policy > 起動プロセスの環境 > env ファイル**で、policy は既存環境も上書きするため信頼できるファイルだけ指定します。パスは実行環境からの相対・絶対位置を事前検証し、許可されない者から読めないよう保護します。存在しない・不正な明示ファイルはエラーです。`PYTHON_DOTENV_DISABLED` が有効な環境では dotenv 読込が無効になり得ます。明示ファイルを読み込んでも全旧設定が profile に変換されるわけではありません。

例は**隔離されたダミー設定専用**で、本番のパスや秘密を引数として貼り付けないでください。既存の環境変数にも注意し、外部サービスを起動しない環境で実施します。

```sh
jllm config validate --profile ./fixture-profile.yaml --env-file ./fixture.env --policy-file ./fixture-policy.env
jllm doctor --profile ./fixture-profile.yaml --env-file ./fixture.env --policy-file ./fixture-policy.env
```

`config validate` は構成の検証、`doctor` は依存解決状態の検査であり、Discord、TTS、LLM、Web 認証、外部 API、ffmpeg の実接続・実動作を確認しません。出力に機密が含まれないか確認してから共有します。

## 2. 隔離環境での実動作ゲート

- 実 Discord 試験は、**専用テスト Bot／テストサーバー／隔離データ／検証用接続先**を用意し、管理者の許可を取って実施する。本番トークンを旧新で共有して同時接続しない。本番接続先に書き込まない。外部 API 利用・課金・音声再生・通知の影響も承認する。
- 許可・拒否対象と例外反応、コマンドと管理権限、VC 接続・読み上げ、辞書・保存と再起動、画像生成停止状態、9 TTS の声・選択・障害時・streaming を確認する。
- LLM・翻訳のモデル／制限、Web 既存パスキーと拒否条件、公開前の RP ID／origin、各保存先・復元・タイマー再開を試す。試験できない箇所を残したまま「完全互換」と判断しない。
- 実テスト Bot で検証できない本番固有項目は、承認された停止時間内に本番トークンを使う**単独稼働**で確認し、項目・担当者・中止基準を事前に決める。

## 3. 承認後の本番切り替え順序

以下は**本番に影響する操作**です。現地のサービス名・対象・権限・状態と各手順を検証し、承認前には実行しません。

1. 停止開始を通知し、旧 Bot と新 Bot の自動再起動／手動起動経路を抑止する。旧 export timer を止め、すでに実行中の export service を完了または安全に停止する。その他すべての writer を停止し、プロセスとサービス状態を独立に確認する。旧新双方が停止し、再起動しないことを確認するまで次に進まない。
2. 停止状態を維持して最終の完全バックアップを取得し、対象漏れ、整合性と復元可否を確認する。バックアップや変換が失敗したら新 Bot を起動しない。停止中に発生した外部イベントや取りこぼしの扱いも記録する。
3. 保護された作業コピーに対して、承認済みの対応表・手順で設定とデータを移行し、対象・権限・参照関係を検証する。旧データに直接上書きしない。検証済みの新用データを明示し、旧・新が同じデータを同時に更新できないよう運用上の排他を維持する。
4. 作業前の最終判定で新側だけの起動を承認する。旧 Bot と旧 export timer／service、その他旧 writer の停止・再起動抑止を再確認し、新側だけを起動する。同一 Discord トークンによる旧新同時接続も禁止する。起動後に実際のプロセス・サービス状態を確認する。
5. 承認済みの最小範囲で新側の実動作を確認する。必要な export 等は書込先と役割を再確認し、**同じデータの writer は同時に最大一つ**という条件を守れる場合だけ、担当者が個別に再開する。失敗時は判定期限を待たず停止・切り戻し判断へ移る。
6. 成功判定、利用者への再開通知、監視、記録を実施。再起動を含む監視中も旧新の排他を守る。バックアップは承認された保管方法・期限に従う。

## 4. 失敗時・新側書き込み後の復旧

1. 新 Bot と新側 timer／ジョブ／他 writer を停止し、自動再起動を抑止する。停止完了を確認するまで旧を起動しない。同一トークン接続も重ねない。
2. 新側で書き込みが発生した場合は、その現状とログを秘密保護の下で保全する。旧スナップショットで新データを無条件に上書きしない。書き込み後の差分、失われうる会話・設定・辞書などと逆変換の可否を評価し、責任者に復旧方法・許容損失を再承認してもらう。
3. 事前に隔離環境で検証した復旧・逆変換手順を適用し、旧の設定、認証、データ、所有権・権限、依存と実動作を確認する。検証可能な復旧方法がない、または損失を許容できない場合は停止を維持して判断を仰ぐ。
4. 旧 Bot だけを起動し、単独接続・単一 writer を確認する。旧 export timer は処理先、実行中ジョブと重複がないことを確認した後に個別に復旧する。新側の自動起動は抑止したままとする。復旧完了と残課題を通知し、監視する。

## 実施記録の最低項目

承認者と担当、revision、検証結果、停止・再開・判断時刻（タイムゾーン付き）、writer の停止確認、バックアップ対象と保管・復元確認、未検証項目、試験結果、損失・例外、切り戻し判断を、アクセス制限された運用記録に残す。秘密値・実 ID・実 URL・個人データは記載しない。
